## Summary

The `shop` repository is a polyglot boundary of 14 deployable units: Go (oms, pricer, three Cosmo
Connect subgraphs, courier-emulation), Rust (delivery), Python/Django (admin), PHP (support),
Next.js (ui, admin-ui) and a Cosmo Router gateway (bff). Nothing from it exists in the catalog
today, so every resource below is `new` except where noted.

Agreed model: **two domains** — `Shop` (catalog, cart, order, pricing, storefront) and `Delivery`
(package and courier lifecycle). The split follows the aggregates, the separate Postgres
instances, the separate Temporal namespaces (`oms` vs `delivery`) and the separate ADR sets, at the
cost of departing from the "one repository = one domain" convention used for Auth and Link.

Two contract conventions coexist and the catalog documents both honestly:

- **Shop/OMS follows [[adr-platform-0002-canonical-event-naming]].** The CQRS bus builds the topic
  from `EventType()` via `cqrsmessage.NewShortlinkNamer("oms")` (`oms/internal/di/event_bus.go:42`),
  so there is exactly one topic per event, as in the Link domain. Serialization is **JSON**
  (`NewJSONMarshaler`), not Protobuf as in Link. Delivery to Kafka goes through a transactional
  outbox in Postgres with a forwarder (`oms/docs/ADR/decisions/0005-reliable-domain-events-outbox.md`).
- **Delivery does not.** `delivery/src/domain/model/delivery/events/v1/events.proto` declares nine
  canonical per-event names, but `delivery/src/infrastructure/messaging/kafka_publisher.rs:33`
  publishes into four topics consolidated by entity lifecycle, and OMS subscribes to the
  consolidated `delivery.package.status.v1` (`oms/internal/infrastructure/kafka/delivery_consumer.go:34`).
  **Channels model the four real topics**; the nine events each point at the topic they actually
  flow through, and the deviation is stated in the Delivery domain page.

### Shop / order-system (status: new)

### Shop / storefront-system (status: new)

### Delivery / delivery-system (status: new)

### Delivery / courier-emulation-system (status: new)
Simulated courier behaviour for exercising the delivery path. Not a production path.

## External systems (top level, `scope: external`)

- **osrm** (status: new) — Open Source Routing Machine. No application code in the repository, only
  `osrm/openapi/openapi.yaml` and a Helm chart. Consumed by CourierEmulationService for route
  simulation (`courier-emulation/internal/infrastructure/osrm`).
- **temporal** (status: new) — workflow engine shared by OMSService and DeliveryService, separate
  namespaces `oms` and `delivery` (`oms/ops/oms/values.yaml`, `delivery/ops/*/values.yaml`).
  Modelled as a system rather than a container because `container_type` has no workflow-engine value
  and because two domains depend on it.

Kafka is deliberately **not** a resource — it is expressed through `protocols: [kafka]` on channels,
matching how the Link domain models it.

## Schemas

The catalog's rule is that copied schemas are owned by `scripts/sync-schemas.mjs`, never copied by
hand (README, "Schemas"). This plan therefore requires **new `FILES` entries in that script** before
any `schema.proto` lands:

- `repo: 'shortlink-org/shop'` — a second upstream repository for the script, which currently only
  references `shortlink-org/shortlink`. No code change is needed: `fetchRaw` builds the raw URL from
  each entry's own `repo` field (`scripts/sync-schemas.mjs:90`).
- Per-message extraction (`derive: { message: '...' }`) for the event schemas — `events.proto` holds
  nine messages in Delivery and seven in OMS order, and the catalog convention is one `schema.proto`
  per event.
- `derive: 'verbatim'` for the RPC protos backing commands and queries.
- `derive: 'openapi-bundle'` for `admin/docs/public/Shop Admin API.yaml` → `AdminService/api.yaml`.

`.github/workflows/schemas.yml` will then cover shop drift on the same daily schedule. Its
`pull_request.paths` filter needs the new proto paths added.

## Open decisions / rationale

- Two domains rather than one, against the "repository = domain" precedent of Auth and Link — chosen
  for the aggregate, storage, Temporal-namespace and ADR separation.
- Delivery channels model the four topics that exist, not the nine names the proto comments claim.
  The gap is documented in the Delivery domain page rather than silently resolved either way.
- `StockChange` is documented with a "Not implemented" badge instead of being omitted.
- Kafka is not modelled as a resource; Temporal and OSRM are, as external top-level systems.
- **To confirm at review:** placement of the two skeleton services — EmailSubscriptionService in
  Shop/catalog-system, SupportService in Delivery/delivery-system.
- The root `README.md` of the shop repository is stale in three places: it lists `geolocation` as a
  service (no such directory), links support and geolocation at `./boundaries/delivery/...` paths
  that do not exist, and calls email-subscription "Python (Django)" when it is a Go skeleton. The
  catalog documents what the code shows, not the table.

## What changed during generation

Four things in this plan turned out to be wrong once the code was read closely. The catalog follows
the code; this section records the corrections.

1. **Delivery has seven channels, not four.** The four outbound topics were right, but the Strimzi
   `KafkaTopic` declarations in `delivery/ops/delivery/values.yaml` also declare three **inbound**
   topics from the courier side: `delivery.courier.location_received.v1`,
   `delivery.order.order_picked_up.v1`, `delivery.order.order_delivered.v1`. Three corresponding
   events were added under `CourierEmulationService`.

2. **Shop does not follow ADR-0002 either — only three of ten events do.** The plan asserted Shop was
   canonical. Verified empirically by running `namer.EventName` against the real event types:

   | Event | Actual topic |
   |---|---|
   | OrderCreated / OrderCancelled / OrderCompleted | `oms.order.{created,cancelled,completed}.v1` — canonical |
   | the four delivery-related order events | `oms.order.delivery_*_event.v1` — `_event` suffix leaks from the proto message name |
   | the three cart events | `oms.oms.item_added_event.v1` etc. — plain Go structs, so the namer cannot read an aggregate and falls back to the service name |

   `EventType()` in `event_type.go` and the `EventTopic` enum both state canonical names, and
   `event_bus.go:130` consults neither. Channels carry the real addresses.

3. **Delivery is not triggered by an event.** `oms.order.delivery_requested_event.v1` has no consumer.
   The actual crossing is a synchronous gRPC `AcceptOrder` call from the `RequestDelivery` Temporal
   activity (`oms/internal/workers/order/activities/activities.go`), with Temporal supplying the
   retries. The integration is asymmetric: gRPC out, Kafka back.

4. **`oms/0005` (outbox) is marked `Proposed` but is implemented.** Frontmatter keeps the source
   status; the body records that `event_bus.go` and migration `000005_create_outbox.up.sql` implement
   it. It is also the one ADR written in Russian — ported as a translation rather than a copy.

Commands and queries did get `schemaPath` after all: the contract proto that defines each one is
copied per resource by `sync-schemas.mjs`, the same way the Link queries already work.

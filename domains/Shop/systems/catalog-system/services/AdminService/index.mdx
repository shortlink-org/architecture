## Overview

The authoritative owner of [[entity|Good]] and [[entity|Office]]. It is the one service in the domain that is a
plain CRUD application, and it is written in Django precisely because that is what it is.

## Structure

Two Django apps under `src/domain`, each a bounded slice of reference data:

| App | Entity | Notable |
|-----|--------|---------|
| `goods` | [[entity\|Good]] | UUID pk, `MoneyField` price, Postgres array of tags, `simple_history` |
| `offices` | [[entity\|Office]] | GeoDjango `PointField` (SRID 4326), opening hours |

The office model is why [[container|shop-postgres]] needs PostGIS.

## API

REST, described by `admin/docs/public/Shop Admin API.yaml`.
[[adr|adr-admin-0003-rest-framework]] records the framework choice; [[adr|adr-shop-0004-use-postman-collection-for-api-documentation]]
explains why a Postman collection sits alongside the spec.

Nothing else in the platform calls this REST API directly. [[service|AdminGraphQL]] adapts it into the federated
graph so consumers see GraphQL like everything else.

## Publishes nothing

There is no Kafka producer here. Goods are read synchronously when needed, and change history is kept in
`historical_*` tables by `simple_history` rather than in an event stream.

The one contract that implies otherwise, [[event|StockChange]], is declared in the order engine and implemented on
neither side.

## Operations

Migrations run with a reduced settings module (`settings_migration.py`) that drops Redis and most apps, so a schema
change does not depend on the cache being available.

Metrics come from `django_prometheus` — models are wrapped in `ExportModelOperationsMixin`, so create/update/delete
counts per model are exported without extra instrumentation.

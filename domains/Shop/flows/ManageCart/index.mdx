## A cart is a workflow, not a row

Every change is a signal — ADD, REMOVE, RESET — against a durable Temporal workflow keyed by customer id, so a cart
outlives the browser session and the pod that served it. [[adr|adr-oms-0003-temporal]] made that choice.

## Write, then read

All three mutations return `google.protobuf.Empty`. The storefront learns what the cart now contains by asking
[[query|GetCart]] — the command side never answers with state.

## The events have no consumers

`CartItemAdded`, `CartItemRemoved` and `CartReset` reach Kafka through the transactional outbox exactly like the
order events do, and nothing subscribes to them. They are there so the cart's history is on the bus, not because
something downstream is waiting.

## Where it goes next

Turning the cart into an order is [[flow|Checkout]].

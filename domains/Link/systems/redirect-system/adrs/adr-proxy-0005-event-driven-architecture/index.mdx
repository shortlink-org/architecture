## Context

After a redirect is served there is asynchronous work to do: publish `LinkRedirected` to the message bus, feed
statistics collection, and leave room for future handlers such as analytics and notifications.

Two requirements followed: keep the synchronous redirect separate from that work, and allow new handlers to be added
without touching existing code.

## Decision

Implement the notification pattern through an `EventDispatcher`:

```
domain/events/LinkRedirectedEvent.ts     the domain event
application/use-cases/PublishEventUseCase.ts
application/handlers/EventDispatcher.ts  registers many handlers per event
application/handlers/IEventHandler.ts
application/handlers/LinkRedirectedEventHandler.ts
```

Multiple handlers can register for one event; the dispatcher notifies all of them.

## Consequences

Publishing cannot delay or fail a redirect — a broker outage costs events, not availability. Adding a consumer inside
the proxy means adding a handler, not editing the redirect path.

The other side of that trade: event delivery is best-effort from the proxy's point of view, so
[[event|LinkRedirected]] must not be treated as a reliable count of visits.

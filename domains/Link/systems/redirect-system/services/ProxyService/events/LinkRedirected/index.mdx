## Overview

The only event produced on the read path. [[service|ProxyService]] publishes it **after** the redirect has been
served, through the notification pattern described in
[[adr|adr-proxy-0005-event-driven-architecture]] — event publishing is deliberately outside the synchronous redirect,
so a broker problem cannot make a redirect fail or slow.

> [!NOTE]
> The payload is the `infrastructure.rpc.link.v1.Link` message — the same message the RPC API returns, reused as the
> event body. There is no dedicated `LinkRedirected` message: "a redirect happened" lives entirely in the topic name,
> and the event carries no timestamp, referrer, user agent or user id of its own. Anything analytical about the
> redirect has to come from elsewhere.

## Delivery

| | |
|---|---|
| Canonical name | `link.link.redirected.v1` |
| Broker | Kafka in production; AMQP fanout exchange when running on RabbitMQ |
| Serialization | Protobuf, `toBinary(LinkSchema, …)` from `@bufbuild/protobuf` |
| Trace context | `traceparent` (and `tracestate` when present) are set in the message headers |

The trace headers matter: they let a consumer resume the same OpenTelemetry trace with
`propagation.extract`, so a redirect and its downstream processing appear as one trace rather than two.

## Legacy topic

`ProxyService` also declares the pre-standard exchange `shortlink.link.event.new`, kept for backward compatibility.
New consumers should bind to `link.link.redirected.v1`.

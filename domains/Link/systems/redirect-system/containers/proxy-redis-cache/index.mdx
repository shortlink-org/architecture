## What is this?

The reason **anonymous** redirects are fast. [[service|ProxyService]] checks Redis before calling
[[service|LinkService]] over gRPC — but only when the request carries no user id.

| | TTL |
|---|---|
| Positive — link found | ~1 hour |
| Negative — link missing | ~5 minutes |

Key format: `${CACHE_KEY_PREFIX}:hash:${hash}`.

### Authenticated requests bypass it

The key is the hash alone, with nothing about the caller — so a private link could otherwise be cached by one
visitor and served to another. `LinkServiceRepository.findByHash` avoids that bluntly: if a `user_id` is present it
goes straight to the adapter and never touches Redis. The code says so, with a `TODO` about a user-aware key.

The consequence is a real one for capacity planning: a logged-in visitor pays a gRPC call on every single redirect,
and the cache hit ratio describes anonymous traffic only.

### Graceful degradation

If Redis is unavailable the proxy keeps serving redirects, falling back to the gRPC call. The cache is an
optimisation, never a dependency — see [[adr|adr-proxy-0007-redis-caching]].

### Staleness

Nothing invalidates this cache on [[event|LinkUpdated]] or [[event|LinkDeleted]] — entries simply expire. A link
edited or removed through the API can therefore keep redirecting to its old target for up to the positive TTL.

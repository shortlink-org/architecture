## Overview

A stand-in for a courier's phone. Without it there is no way to exercise the delivery path end to end: packages
would be assigned and never move.

## What it does

1. Consumes an assignment off [[channel|delivery.order.assigned.v1]] — the JSON copy of
   [[event|PackageAssigned]] published specifically for this consumer
2. Asks [[system|osrm]] for a route between pickup and delivery addresses
3. Walks the polyline at a configurable speed, publishing [[event|CourierLocationReceived]] as it goes
4. Confirms pickup with [[event|OrderPickedUp]], then delivery with [[event|OrderDelivered]]

[[service|DeliveryService]] consumes all three, so the package advances through its state machine exactly as it
would with a real courier.

## Topic naming does not follow the outbound convention

The three topics it publishes are named for what the receiver does with them — `location_received`,
`order_picked_up`, `order_delivered` — rather than for a package or courier lifecycle event. They are inbound
topics from the Delivery service's point of view, declared as such in its Strimzi configuration.

## It is a test fixture

This service exists to make non-production environments behave. It is in its own system so that a reader tracing
the production delivery path does not have to work out which of the two Go services is real.

The [[event|PackageAssigned]] it reacts to is a copy; the authoritative record of an assignment is the protobuf
event on [[channel|delivery.package.status.v1]].

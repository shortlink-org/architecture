## What is this?

Three jobs in one instance, all of them in `delivery/src/infrastructure`:

| Role | Code |
|------|------|
| Courier cache | `cache/courier_redis.rs` |
| Current courier location, TTL'd | `cache/location_redis.rs` |
| Tracking fan-out | `messaging/tracking_pubsub.rs` |

## Why location lives here rather than in Postgres

Couriers report position continuously. Dispatch needs the *latest* position of every candidate courier on every
assignment — a read pattern that has nothing in common with an append-only history table.

So the current position is a TTL'd key in Redis and the trail is
`courier_location_history` in [[container|delivery-postgres]]. A stale key simply means a courier has stopped
reporting, which is information dispatch wants anyway.

## Why tracking needs pub/sub

[[query|SubscribeOrderTracking]] is a server-streaming RPC: a customer watching their package holds an open stream
and expects a new snapshot whenever state changes. The state change happens in whichever replica handled the
transition, and the stream is held by whichever replica the customer connected to.

Redis pub/sub is what carries the notification between them. Without it, live tracking would only work when both
ends happened to land on the same pod.

## Losing it is survivable

Nothing authoritative. A restart costs cached couriers, current locations until the next report, and the liveness
of open tracking streams — no package or courier record is at risk.

## Overview

The whole of the [[domain|Delivery]] boundary's logic: [[entity|Package]] and [[entity|Courier]], the state machine
over each, courier dispatch, and the tracking surface the storefront reads.

## Architecture diagram

<NodeGraph />

## Work arrives by gRPC, results leave by Kafka

This service consumes no `oms.*` topic. [[service|OMSService]] calls [[command|AcceptOrder]] directly, from inside
a Temporal activity that supplies the retries and durability a broker would otherwise provide.

Everything the boundary has to say goes back out as events. That asymmetry is deliberate: the request needs an
answer (a `package_id`, synchronously), the status updates do not.

## Layout

| Layer | Contents |
|-------|----------|
| `domain/model/` | aggregates, value objects, generated protobuf types |
| `domain/services/` | `DispatchService`, `AssignmentValidationService` — pure logic |
| `usecases/` | one directory per command and query, each with a README |
| `infrastructure/` | sea-orm repositories, Redis caches, Kafka, tracking pub/sub |

[[adr|adr-delivery-0003-domain-structure]] fixes the model/services split.

## Dispatch

`AssignOrder` carries a `oneof`: an explicit `courier_id`, or `auto_assign`. Automatic dispatch filters candidates
on status, remaining capacity and work zone, then sorts by Haversine distance from the courier's last known
position — read from [[container|delivery-redis]], not from Postgres.
See [[adr|adr-delivery-0004-dispatching-and-geolocation]].

## Three inbound topics

| Topic | Carries | Configured by |
|-------|---------|---------------|
| [[channel\|delivery.courier.location_received.v1]] | courier positions | `KAFKA_LOCATION_TOPIC` |
| [[channel\|delivery.order.order_picked_up.v1]] | pickup confirmations | `KAFKA_PICKUP_TOPIC` |
| [[channel\|delivery.order.order_delivered.v1]] | delivery confirmations | `KAFKA_DELIVERY_RESULT_TOPIC` |

> [!NOTE]
> The location consumer's compiled-in default is `courier.location.updates`, which is **not** a topic that exists.
> The deployment overrides it to `delivery.courier.location_received.v1`
> (`delivery/ops/delivery/values.yaml`). Reading the Rust constant alone will give you the wrong topic name.

## Outbox, like the order side

Events are written to `outbox_messages` in [[container|delivery-postgres]] in the same transaction as the aggregate,
and an `outbox_forwarder` publishes them to Kafka afterwards. The two boundaries arrived at the same pattern
independently, in different languages.

## Tracking is streamed

[[query|SubscribeOrderTracking]] is the only server-streaming RPC in the catalogue. State changes happen in whichever
replica handled the transition; the stream is held by whichever replica the customer reached. Redis pub/sub carries
the notification between them.

Both tracking queries are keyed by **OMS order id**, not package id — they exist for a caller in the other boundary
who has never seen a package.

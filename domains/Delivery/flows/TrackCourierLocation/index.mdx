## Why this never became an RPC

`UpdateCourierLocation` exists in the domain model and has no RPC on [[service|DeliveryService]]. Couriers report
continuously, and putting that on the gRPC API would tie the fleet's reporting rate to the API's availability for
data whose value expires in seconds.

## Two location topics, opposite directions

| Topic | Direction |
|-------|-----------|
| [[channel\|delivery.courier.location_received.v1]] | inbound, from the courier side |
| [[channel\|delivery.courier.location.v1]] | outbound, the domain event |

The consuming side's compiled-in default is `courier.location.updates`, a topic that does not exist. The real name
comes from `KAFKA_LOCATION_TOPIC` in the delivery Helm values — reading the Rust constant alone is misleading.

## The producer is a test fixture, the contract is not

Today the only publisher is [[service|CourierEmulationService]], which exists so non-production environments move
packages at all. The event models a courier's phone, and a real courier app would publish exactly this.

## What the position is for

Dispatch. Auto-assignment sorts candidates by Haversine distance from the cached position — see
[[adr|adr-delivery-0004-dispatching-and-geolocation]] and [[flow|DeliverPackage]].

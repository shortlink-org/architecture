## Overview

## Created on acceptance, not on order

A package does not exist because an order was placed. It exists because the Delivery boundary **accepted** a
delivery request — [[command|AcceptOrder]]. Orders that never ship never produce one.

## Lifecycle

Every transition emits an event, and all six share [[channel|delivery.package.status.v1]]:

| Transition | Command | Event |
|-----------|---------|-------|
| → ACCEPTED | [[command\|AcceptOrder]] | [[event\|PackageAccepted]] |
| → ASSIGNED | [[command\|AssignOrder]] | [[event\|PackageAssigned]] |
| → IN_TRANSIT | [[command\|PickUpOrder]] | [[event\|PackageInTransit]] |
| → DELIVERED | [[command\|DeliverOrder]] | [[event\|PackageDelivered]] |
| → NOT_DELIVERED | [[command\|DeliverOrder]] | [[event\|PackageNotDelivered]] |
| → REQUIRES_HANDLING | — | [[event\|PackageRequiresHandling]] |

`REQUIRES_HANDLING` is the escape hatch: a package that cannot proceed automatically and needs a human.

## Failure is structured

An earlier schema stored a free-text `not_delivered_reason`; migration `m20260316_000009` dropped it. The reason is
now an enum with a description that is required only for `OTHER`, so a downstream system can tell "customer not
available" from "wrong address" without parsing prose.

## The order reference is not a foreign key

`order_id` points into another boundary and another database. Nothing joins on it — it exists so that
[[service|OMSService]] can match a status event back to its order, and so tracking can be looked up by order id in
[[query|GetOrderTracking]].

## Overview

Authentication tells a service *who* is calling. This system tells it *whether they may*. It stores no roles and no
ACL rows — permissions are computed by walking relationships in [[container|spicedb]].

[[service|AuthService]] is deliberately thin: it owns and migrates the schema. The actual `CheckPermission` calls
are made by the consuming services (BFF, link, metadata) directly against SpiceDB over gRPC.

## The schema

```
definition user {}

definition anonymoususer {}

definition team {
    relation administrator: user
    relation member: user
    permission view_all_links = administrator
}

definition link {
    relation linkteam: team
    relation reader: user | team#member | anonymoususer:*
    relation writer: user

    permission edit = writer
    permission view = reader + writer + linkteam->view_all_links
}
```

Three things worth reading twice:

1. **`anonymoususer:*` on `reader`** — the wildcard is how a link becomes public. One tuple grants read to every
   unauthenticated visitor.
2. **`linkteam->view_all_links`** — a team administrator can view every link the team owns without any tuple
   existing between that administrator and the link.
3. **`edit = writer` only** — being a team administrator does *not* grant edit. The schema's own assertions pin
   this: `link:firstlink#edit@user:admin` must be false.

## Example relationships

```
link:firstlink#writer@user:tom
link:firstlink#reader@user:fred
link:firstlink#linkteam@team:team1
team:team1#administrator@user:admin
```

Derived from those four tuples: Tom can view and edit; Fred can view but not edit; Admin can view (via the team)
but not edit.

## Boundary note

The `link` definition lives in this schema but the concept belongs to the Link boundary. The permission model is
centralised even though the resources it protects are not — changing what `view` means for a link is a change to
this system.

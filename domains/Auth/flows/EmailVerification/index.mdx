## Why the account works before it is verified

Registration runs two after-hooks on the password path: `session`, which signs the visitor straight in, and
`show_verification_ui`. The first makes the account immediately usable, so verification is a background errand
rather than a step in the journey — see [[flow|UserRegistration]].

## Nothing downstream reads it

[[service|Oathkeeper]]'s `id_token` mutator puts `sub`, `email`, `name`, `identity_id`, `session_id` and public
metadata into the JWT. Verified status is not among them, so no service behind the edge can make a decision on it
even if it wanted to.

## Only the password path

`show_verification_ui` is one of the two after-hooks documented on the registration **password** path. An identity
created through GitHub or GitLab is never sent this code.
